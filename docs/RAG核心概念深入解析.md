# RAG 核心概念深入解析

## 一、余弦相似度 (Cosine Similarity)

### 基本定义

余弦相似度通过计算两个向量之间夹角的余弦值来衡量相似性：

```
cos(A, B) = A · B / (|A| × |B|)

其中：
  A · B  = Σ(aᵢ × bᵢ)     向量点积
  |A|    = √(Σaᵢ²)        向量 A 的模（长度）
  |B|    = √(Σbᵢ²)        向量 B 的模（长度）
```

### 具体例子

假设我们有两个 3 维向量（实际 Embedding 通常是 768/1536 维，但原理一样）：

```
文档 A "猫吃鱼":   A = [4, 3, 0]
文档 B "猫喝牛奶":  B = [8, 6, 0]
文档 C "飞机飞行":  C = [0, 1, 1]
```

**第一步：计算模（长度）**

```
|A| = √(16 + 9 + 0)  = √25 = 5
|B| = √(64 + 36 + 0) = √100 = 10
|C| = √(0 + 1 + 1)   = √2 ≈ 1.41
```

**第二步：计算余弦相似度**

```
A vs B:  cos = (4×8 + 3×6 + 0×0) / (5 × 10) = 50 / 50 = 1.00  ← 完全相同方向
A vs C:  cos = (4×0 + 3×1 + 0×1) / (5 × 1.41) = 3 / 7.07 ≈ 0.42  ← 有一定关联
B vs C:  cos = (8×0 + 6×1 + 0×1) / (10 × 1.41) = 6 / 14.1 ≈ 0.43  ← 有一定关联
```

> A 和 B 的余弦相似度是 **1.0**，虽然 B 的每个维度都是 A 的 2 倍（长度不同），但它们**方向完全相同**，说明语义一致。这就是余弦相似度的关键特性——**只看方向，不看大小**。

### 几何直觉

想象每个向量是从原点出发的箭头：

```
        y
        │      C
        │     ╱
        │    ╱
        │   ╱ θ₂
        │  ╱
        │ ╱ θ₁
        │╱___________________ x
       O    A
          B
```

- A 和 B 几乎重叠 → `cos(θ₁) ≈ 1` → 语义非常相似
- A 和 C 夹角较大 → `cos(θ₂) ≈ 0.42` → 有一定相关性但不大
- 如果 C 跑到 x 轴负方向 → `cos(θ) = -1` → 完全对立

### 余弦相似度 vs 其他距离度量

| 度量方式 | 公式 | 是否受向量长度影响 | 典型场景 |
|---------|------|:-:|---------|
| **Cosine Similarity** | cos(θ) | 否 | 文本语义相似度 |
| Euclidean Distance | √(Σ(aᵢ-bᵢ)²) | **是** | 图像特征、物理距离 |
| Dot Product | A · B | **是** | 向量已归一化时等价于 Cosine |
| Manhattan Distance | Σ\|aᵢ-bᵢ\| | **是** | 网格路径、推荐系统 |

### 为什么文本检索首选余弦相似度？

**问题场景**：假设 Embedding 空间中，向量的长度与文本长度正相关：

```
短句:  "猫"          → 长度小，但方向指向"动物"语义
长文:  "猫是哺乳动物..."  → 长度大，但方向同样指向"动物"语义
```

如果用欧氏距离，长文的向量离原点远，短句离原点近，两者距离会很远——**但它俩明明说的是同类东西**。

而余弦相似度只看方向：

- 两者的向量方向几乎一致 → `cos ≈ 1` → 正确判定为语义相似

### RAG 中的实际应用

```python
import numpy as np

# 两个 chunk 的 embedding（简化为 5 维演示）
chunk_1 = np.array([0.82, 0.15, 0.33, 0.71, 0.29])
chunk_2 = np.array([0.78, 0.21, 0.30, 0.68, 0.31])

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(cosine_similarity(chunk_1, chunk_2))
# → 0.997  非常相似
```

实际 RAG 流程中，当用户提问时：

1. 把问题转成向量
2. 与向量库中**数万甚至数十万个** chunk 向量逐一计算余弦相似度
3. 取相似度最高的 top-K（如 K=5）个 chunk
4. 这些 chunk 作为上下文送给 LLM 生成回答

为了加速这个"逐一计算"的过程，生产环境通常使用 **HNSW** 等近似最近邻（ANN）索引，而不是暴力遍历。

## 二、文本切块 (Chunking)

### 为什么要切块？

这是 RAG 系统中**最容易被低估但对检索质量影响最大的环节**。

直接把整篇文档做 Embedding 会有三个问题：

**问题 1: Token 上限**

```
Embedding 模型通常有 max token 限制
text-embedding-3-small: 8192 tokens
bge-large-zh:           512 tokens  ← 中文常用模型，限制很小！
```

**问题 2: 语义稀释**

```
一篇 10 页的文档包含：公司介绍、技术架构、招聘信息...
做成一个向量后 → 语义被"平均化"了
用户问"技术栈是什么" → 检索到的 chunk 里招聘信息占了 60%
                        → 相关内容被淹没
```

**问题 3: 检索粒度**

```
返回整篇文档给 LLM → 噪音太多、token 浪费
返回精确的一段话    → 上下文干净、回答精准
```

### 切块的核心参数

切块不是简单的一刀切，需要调这几个参数：

```
┌─────────────────────────────────────────────┐
│              Chunking 策略                    │
│                                              │
│  chunk_size  ── 每块的大小 (字数/token数)    │
│  chunk_overlap ── 块之间的重叠部分            │
│  separator  ── 切分边界 (按什么规则切)       │
│  metadata  ── 每块附带什么元信息             │
└─────────────────────────────────────────────┘
```

#### chunk_size：多大合适？

没有万能答案，取决于场景：

| 文档类型 | 建议 chunk_size | 原因 |
|---------|:-:|------|
| FAQ / 问答对 | 200-300 字 | 内容短小，不需要大块 |
| 技术文档/API | 500-800 字 | 需要保留代码和解释的完整上下文 |
| 法律合同 | 800-1200 字 | 条款有上下文依赖，太短会断章取义 |
| 学术论文 | 1000-1500 字 | 段落之间有逻辑递进 |
| 小说/长文 | 500-1000 字 | 保持叙事连贯 |

#### chunk_overlap：为什么要有重叠？

没有重叠会丢失边界信息：

```
没有重叠:
──────────────────────────────────────────────
chunk_1: "...介绍了 REST API 的基本概念"
chunk_2: "GET 请求用于获取资源..."           ← 丢失了 chunk_1 末尾的上下文
chunk_3: "POST 请求用于创建..."
                                        用户问"GET 请求是什么？"
                                        chunk_2 被检索到
                                        但 chunk_2 缺少前文衔接

有重叠 (overlap = 50 字):
──────────────────────────────────────────────
chunk_1: "...介绍了 REST API 的基本概念"
chunk_2: "REST API 的基本概念，GET 请求用于获取资源..."  ← 有前文衔接
chunk_3: "GET 请求用于获取资源，POST 请求用于创建..."   ← 有前文衔接
```

常见重叠比例：chunk_size 的 **10%-25%**（例如 500 字的块，重叠 50-125 字）。

### 六种常见切块策略

#### 1. 固定长度切块

最简单粗暴的方式：

```python
text = "第一条：甲方应按时付款。第二条：乙方应按时交付。第三条：违约金为合同金额的10%。"

# 每 10 字切一块
chunks = [text[i:i+10] for i in range(0, len(text), 10)]

# 结果:
# chunk_0: "第一条：甲方应按时付款"        ✓ 语义完整
# chunk_1: "。第二条：乙方应按时交付"       ✗ 以"。"开头，断句奇怪
# chunk_2: "。第三条：违约金为合同金额"     ✗ 同上
```

**问题**：会在句子中间截断，破坏语义。实际很少单独使用。

#### 2. 递归字符切块

LlamaIndex 和 LangChain 的默认策略。按优先级尝试多种分隔符：

```
分隔符优先级（从粗到细）:
  "\n\n"  →  段落
  "\n"    →  换行
  "。"    →  句子（中文）
  "."     →  句子（英文）
  " "     →  空格（英文）
  ""      →  单字（兜底）
```

```
工作流程:
─────────────────────────────
目标: chunk_size = 500

  1. 尝试按 "\n\n" 切
     → 如果每段都 ≤ 500  → 完成 ✓
     → 如果某段 > 500    → 进入下一步

  2. 对超长段按 "\n" 切
     → 如果每行都 ≤ 500  → 完成 ✓
     → 如果某行 > 500    → 进入下一步

  3. 对超长行按 "。" 切
     → ...依此类推，直到每块 ≤ 500
```

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", ".", " ", ""],  # 优先级从左到右
)

chunks = splitter.split_text(long_document)
```

**优点**：自动适配不同格式，是大多数项目的起点。

#### 3. 文档结构切块

利用文档自身的结构信息：

```
Markdown 文档:
─────────────────────────────
# 第一章 概述          ← 按 # 切
  ## 1.1 背景          ← 按 ## 切
  ## 1.2 目标
# 第二章 技术方案
  ## 2.1 架构
  ## 2.2 实现

HTML 文档:
─────────────────────────────
<h1>  <h2>  <h3>  <p>  <table>   ← 按 HTML 标签切

PDF 文档:
─────────────────────────────
页眉  标题  正文  页脚  表格  图片标题   ← 按视觉元素切
```

```python
from langchain.text_splitter import MarkdownHeaderTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]

splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)
chunks = splitter.split_text(markdown_document)

# 每个 chunk 会自动附带 header 信息作为 metadata:
# chunk.content = "这段内容..."
# chunk.metadata = {"Header 1": "第二章 技术方案", "Header 2": "2.1 架构"}
```

**关键优势**：切出来的块天然带有**层级上下文**，检索时可以告诉 LLM "这段内容来自哪一章节"。

#### 4. 语义切块

不按固定长度，而是按语义的**自然断点**切分：

```
原理:
─────────────────────────────
  1. 对文本中的每个句子计算 Embedding
  2. 计算相邻两个句子 Embedding 之间的余弦相似度
  3. 相似度突然下降的地方 → 语义转折点 → 在这里切一刀

  句子1: "React 是一个前端框架。"
  句子2: "它使用虚拟 DOM 来提升性能。"    ← 与句1相似度高
  句子3: "公司的办公地址在北京朝阳区。"    ← 与句2相似度骤降 → 切！
```

```python
from semantic_text_splitter import SemanticSplitter
# 或者用 semchunk 库
from semchunk import semchunk

chunks = semchunk(text, chunk_size=500)
```

**优点**：每次切出的块语义完整、自然。

**缺点**：需要对每个句子做 Embedding，**速度慢、成本高**。10 万字的文档可能要调几千次 Embedding API。

#### 5. 句子级切块

把每个句子作为一个独立 chunk：

```python
text = "天气很好。我去公园散步。遇到了老朋友。"

chunks = ["天气很好。", "我去公园散步。", "遇到了老朋友。"]
```

**适用场景**：精确问答、事实检索。

**问题**：太碎了，缺少上下文。

#### 6. 父子块 (Parent-Child Chunking)

一种结合策略，用小块检索，用大块提供上下文：

```
                    ┌─ child_1: " useState 用于..."
                    │
parent_chunk:       ├─ child_2: " useEffect 用于..."
"React Hooks 简介   │
useState, useEffect, └─ child_3: " useRef 用于..."
useRef 等钩子的用法"
```

```
工作流程:
─────────────────────────────
  1. 文档切成大块 (parent, 如 1000 字)
  2. 每个大块再切成小块 (child, 如 200 字)
  3. Embedding 和检索只对 child 做
  4. 命中的 child 找到它的 parent
  5. 把整个 parent 作为上下文送给 LLM

  用户提问: "useState 怎么用？"
  → 检索命中 child_1
  → 返回整个 parent_chunk（包含了 useState/useEffect/useRef 的完整上下文）
```

**优势**：小块保证检索精度，大块保证上下文完整性。这是**生产环境中非常推荐的方案**。

### Metadata：常被忽略但至关重要

切块不只是切文本，还要给每块附带元信息：

```python
chunk = {
    "content": "useState 是 React 最基本的 Hook...",
    "metadata": {
        "source": "react-hooks-guide.md",     # 来源文件
        "page": 3,                              # 页码
        "header": "2.1 useState",              # 所属章节
        "author": "张三",                       # 作者
        "date": "2025-01-15",                  # 文档日期
        "chunk_index": 5,                       # 第几块
    }
}
```

Metadata 的作用：

- **过滤**：用户问"2025 年的政策"，直接过滤 `date < 2025` 的 chunk
- **溯源**：LLM 回答时可以标注"来源：react-hooks-guide.md 第 3 页"
- **权限**：根据用户角色过滤有权限的文档 chunk

### 切块策略选择指南

```
你的文档是什么类型？
│
├── 结构化文档（Markdown/HTML/带标题的文档）
│   └── 文档结构切块 + metadata  ← 首选
│
├── 非结构化长文本（论文/合同/小说）
│   ├── 对质量要求高 → 语义切块
│   └── 对速度要求高 → 递归字符切块
│
├── FAQ / 问答对
│   └── 按问答对切块，一个 Q+A = 一个 chunk
│
├── 代码文档
│   └── 按函数/类切块，保留代码结构
│
└── 通用场景 / 不确定
    └── 递归字符切块 (LangChain 默认) → 跑起来 → 根据效果调优
```
